# MasterHub — звіт по курсовій роботі

## 1. Мета та результат

Побудувати застосунок і пройти його повний життєвий цикл: від аналізу домену й контракту API до контейнерів, CI/CD, спостережуваності та Kubernetes. Результат — MasterHub, маркетплейс перевірених майстрів, що працює як Docker Compose-стек і розгортається в Minikube.

## 3. Ключові рішення

- **Модульний моноліт замість мікросервісів** (ADR 0001): один автор, один деплой; межі піддоменів тримаються структурою `domain/`.
- **Шари `api → service → domain` + `repository`** (ADR 0002): HTTP, бізнес-логіка та зберігання змінюються незалежно, тести сервісів не потребують БД.
- **Єдиний формат помилки з `requestId`** (ADR 0003): помилку з UI можна знайти в логах і трейсах за одним ідентифікатором.
- **Ідемпотентне створення замовлень**: повторний клік чи ретрай не створює дубль.
- **Архівування замість видалення довідників**: старі замовлення зберігають посилання на майстра й послугу.
- **Один образ API для Compose і Kubernetes**: конфігурація лише через змінні середовища.

## 4. Спостережуваність і алерти

Дашборд `MasterHub RED` показує RPS, частку 5xx, p95 latency, JSON-логи та список алертів.

| Алерт | Умова | Вікно | Що робити при спрацюванні |
|---|---|---|---|
| 5xx error rate | частка відповідей 5xx > 5 % | 5 хв, `for: 2m` | Перевірити `/health/details`, логи рівня error у Loki, трейси в Tempo; за 503 — стан PostgreSQL |
| p95 latency | p95 > 500 мс | 5 хв, `for: 2m` | Знайти повільні трейси в Tempo, перевірити БД і RPS |

Обидва алерти корисні в проді: перший ловить несправності, які бачать користувачі, другий — деградацію до того, як почнуться помилки.

## 6. Kubernetes: відповіді на контрольні запитання

**ConfigMap і Secret.** ConfigMap зберігає нечутливу конфігурацію відкритим текстом; Secret — чутливі значення (base64, з обмеженим доступом через RBAC).

**Liveness і readiness.** Liveness відповідає «процес живий?» і за провалу перезапускає контейнер; readiness — «готовий приймати трафік?» і за провалу виводить Pod із Service без перезапуску. У MasterHub: `/healthz` та `/ready`.

**Шлях запиту.** Через `kubectl port-forward`: клієнт → port-forward → Service → Pod. Через `http://masterhub.local`: клієнт → DNS/hosts → Ingress-контролер → Service → Pod.

**Оновлення конфігурації з ConfigMap через env.** Змінні потрапляють у контейнер лише під час його старту, тож після зміни ConfigMap потрібно виконати `kubectl rollout restart deployment/<name>`.

**Самовідновлення.** Після видалення Pod Deployment через ReplicaSet створює новий, щоб кількість реплік відповідала заданій.

## 7. Обмеження та подальша робота

- Сесії зберігаються в пам'яті процесу, тому за кількох реплік API потрібне спільне сховище сесій.
- Піддомени Payments, Verification і Notifications змодельовані в `domain/`, але не мають повноцінної реалізації.
- Контакт-поінт алертів — навчальний webhook без реального приймача.
