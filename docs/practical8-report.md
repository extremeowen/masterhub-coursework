## 2. Завдання на 60 балів (Базовий запуск та дослідження стенду)

### 2.1. Запуск тестового стенду
Стенд розгортається з навчального репозиторію `observability-demo` за допомогою Docker Compose:
```bash
git clone https://github.com/vivalafit/observability-demo
cd observability-demo
docker compose up -d --build
```

**Перевірка доступності сервісів у браузері:**
* **API сервісу:** `http://localhost:3000` (або `http://localhost:8080`)
* **Grafana:** `http://localhost:3001` (вхід: `admin` / `admin`)
* **Prometheus:** `http://localhost:9090`
* **Loki:** `http://localhost:3100`
* **Tempo API/UI:** `http://localhost:3200`

### 2.2. Генерація навантаження та аналіз стандартних сигналів
Генерація трафіку забезпечується автоматичним контейнером `loadgen` або тестовими запитами:
```bash
# Тестові запити для генерації успішних відповідей та помилок:
curl http://localhost:3000/api/status
curl http://localhost:3000/api/items
curl http://localhost:3000/api/slow
curl http://localhost:3000/api/error
```

### 2.3. Результати дослідження компонентів стенду:
1. **RED-дашборд в Grafana (`Observability Demo / RED`):**
   * Графік **Rate (RPS)** показує інтенсивність надходження запитів до сервісу `demo-app`.
   * Графік **Errors** фіксує кількість відповідей з кодами 5xx (згенерованих ендпоінтом `/api/error`).
   * Графік **Duration** демонструє час обробки запитів, де помітні сплески затримки від ендпоінту `/api/slow`.
2. **Трейси у Grafana Explore (Tempo):**
   * У розділі `Explore -> Datasource: Tempo` відображається дерево span-ів для кожного HTTP-запиту. Трейс фіксує точний час проходження запиту крізь middleware, обробники роутів та бази даних, дозволяючи знайти конкретну ділянку сповільнення.
3. **Логи у Grafana Explore (Loki):**
   * Запит `{service_name="demo-app"}` повертає структуровані логи. Кожен запис містить мітку часу, рівень логування (`info`, `error`), а також прив'язку до `trace_id`, що забезпечує швидкий перехід від тексту помилки до відповідного трейсу.

## 3. Завдання на 75 балів (Власний RED-дашборд «My Demo RED»)

На рівні 75 балів створено власний дашборд у Grafana з назвою **`My Demo RED`**, оптимізований для моніторингу сервісу `demo-app`. Дашборд містить 4 ключові панелі, які реалізують класичний шаблон RED (Rate, Errors, Duration) та панель операційних логів.

Всі панелі чутливі до глобального селектора часу Grafana (`Time Range`), що дозволяє проводити ретроспективний аналіз інцидентів за будь-який проміжок (останні 5 хв, 15 хв, 1 година тощо).

Файл дашборду експортовано у репозиторій:
📁 [`docs/my-demo-red-dashboard.json`](my-demo-red-dashboard.json)

---

### 3.1. Панель 1: Requests per second (Rate)
* **Тип панелі:** Time Series (`timeseries`)
* **Одиниця вимірювання:** `reqps` (Requests / sec)
* **Джерело даних:** Prometheus
* **PromQL-запит:**
  ```promql
  sum(rate(http_requests_total[1m]))
  ```
* **Що показує панель:**
  Показує середню швидкість надходження вхідних HTTP-запитів за секунду, розраховану у ковзному 5-хвилинному вікні для сервісу `demo-app`.
* **Використання у продакшені:**
  Дозволяє інженерам відстежувати бізнес-активність користувачів, фіксувати добові піки навантаження, виявляти аномальні спади трафіку (наприклад, збій на рівні DNS або CDN) та раптові сплески (DDoS-атаки або маркетингові акції).

---

### 3.2. Панель 2: Error Rate (% 5xx)
* **Тип панелі:** Time Series (`timeseries`) з кольоровими порогами (Thresholds)
* **Одиниця вимірювання:** `percent` (0–100%)
* **Джерело даних:** Prometheus
* **PromQL-запит:**
  ```promql
  100 * sum(rate(http_requests_error_total[1m])) 
  / 
  clamp_min(sum(rate(http_requests_total[1m])), 0.001)
  ```
* **Налаштування порогів (Thresholds):**
  * `< 1%` — зелена зона (штатний режим);
  * `1% - 5%` — жовта зона (підвищений рівень помилок);
  * `> 5%` — червона зона (критичний інцидент, спрацьовування алерту).
* **Що показує панель:**
  Відсоток невдалих запитів (HTTP статус 500–599) відносно загальної кількості запитів до сервісу. Функція `clamp_min(..., 0.001)` запобігає діленню на нуль у періоди відсутності трафіку.
* **Використання у продакшені:**
  Критична метрика здоров'я сервісу за методологією Google SRE (Service Level Indicator, SLI). Дозволяє миттєво визначити деградацію бекенду після релізу, втрату зв'язку з базою даних або сторонніми API.

---

### 3.3. Панель 3: Latency p95 (Duration)
* **Тип панелі:** Time Series (`timeseries`)
* **Одиниця вимірювання:** `seconds (s)`
* **Джерело даних:** Prometheus
* **PromQL-запит:**
  ```promql
  histogram_quantile(0.95, sum(rate(http_request_duration_ms_bucket[5m])) by (le))
  ```
* **Що показує панель:**
  95-й перцентиль часу обробки запитів. Це означає, що 95% усіх клієнтських запитів виконуються швидше за це значення, і лише 5% найповільніших перевищують його.
* **Використання у продакшені:**
  На відміну від середнього арифметичного (яке згладжує та приховує серйозні проблеми окремих клієнтів), перцентиль p95 чітко показує реальний досвід користувачів у найгірших умовах (наприклад, тривалі блокування в БД, повільні дискові операції або дефіцит CPU).

---

### 3.4. Панель 4: Таблиця логів Loki (service.name=demo-app)
* **Тип панелі:** Logs (`logs`)
* **Джерело даних:** Loki
* **LogQL-запити:**
  * Основний потік логів сервісу demo-app:
    ```logql
    {service="demo-app"}
    ```
  * Фільтрація рядків з помилками:
    ```logql
    {service="demo-app"} |= "error"
    ```
* **Що показує панель:**
  Консолідований список текстових та JSON-логів застосунку у хронологічному порядку зі зворотним сортуванням (найновіші зверху). Фільтр `|= "error"` миттєво виділяє виключення, стектрейси та збійні операції.
* **Використання у продакшені:**
  Коли метрики Error Rate або Latency сигналізують про аномалію, інженер дивиться на панель логів, щоб з'ясувати першопричину збою (root cause) без необхідності підключатися по SSH до сервера чи подов у Kubernetes.

---

### 3.5. Вплив вибору часового періоду (Time Range) на дашборд
У дашборді налаштовано динамічні змінні інтервалу:
* При зміні глобального фільтра часу вгорі Grafana (наприклад, `Last 15 minutes` ➔ `Last 6 hours`):
  * Усі 4 панелі синхронно перебудовують свої осі часу.
  * Вікно `[5m]` у запитах `rate()` гарантує стабільне згладжування шуму на коротких відрізках, а Grafana автоматично адаптує крок дискретизації (`step`), запобігаючи перевантаженню браузера точками даних.
  * Логи у панелі Loki автоматично завантажуються виключно для обраного проміжку часу.
