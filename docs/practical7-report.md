# Звіт до практичної роботи №7
## Тема: CI/CD на GitHub Actions
**Рівень оцінювання:** 75 балів (1 сервіс на вибір у власному репозиторії)

---

## 1. Мета роботи
1. Ознайомитися з концепцією Continuous Integration (CI) та Continuous Delivery (CD).
2. Налаштувати автоматизований пайплайн у **GitHub Actions** для перевірки та тестування бекенд-сервісу курсового проєкту MasterHub.
3. Реалізувати автоматичну збірку контейнерного Docker-образу та його доставку (Delivery) до реєстру пакетів **GitHub Container Registry (GHCR)** за варіантом A (`ghcr.io/<owner>/<repo>-api:<tag>`).
4. Налаштувати артефакти звітності тестів (JUnit XML), бейдж статусу збірки у `README.md`, кешування залежностей та безпечні права доступу (`permissions`).

---

## 2. Обраний сервіс та підхід до Delivery (Рівень 75 балів)

* **Обраний сервіс проєкту:** `api` (основний REST API бекенд на Node.js/Express).
* **Середовище виконання:** Ubuntu Linux (`ubuntu-latest`), Node.js версії 22 LTS.
* **Підхід до Delivery:** **Варіант A — GHCR**. Образ автоматично збирається з [`Dockerfile`](../Dockerfile) та публікується за адресою:
  `ghcr.io/<github-username>/masterhub-coursework-api:<tag>`
* **Політика тегування образів:**
  1. `sha-<short-sha>` — унікальний хеш коміту для трасування конкретної збірки.
  2. `latest` — автоматичний тег для останньої стабільної версії з гілки `main`.
  3. `vX.Y.Z` — семантичні релізні теги за наявності git-тегу.

---

## 3. Опис конфігурації CI/CD ([`.github/workflows/ci.yml`](../.github/workflows/ci.yml))

Пайплайн складається з двох послідовних етапів: **Test** (перевірка якості коду) та **Publish** (доставка образу в реєстр контейнерів).

### 3.1. Тригери запуску
* `push` у гілку `main` та при створенні релізних тегів `v*`.
* `pull_request` — перевіряє код перед злиттям у `main` (етап доставки для PR блокується, виконуються тільки тести).
* `workflow_dispatch` — можливість ручного запуску пайплайну в один клік з інтерфейсу GitHub.

### 3.2. Захист та оптимізація виконання
* **`concurrency.cancel-in-progress: true`**: якщо розробник робить новий коміт у ту саму гілку, попереднє виконання, що ще триває, автоматично скасовується для економії ресурсів CI.
* **`permissions`**: за замовчуванням пайплайн має мінімальні права лише на читання коду (`contents: read`). Дозвіл на запис у реєстр пакетів (`packages: write`) видається виключно етапу публікації образу.

---

### 3.3. Етап 1: Тестування (`job: test`)
1. **Checkout коду**: використовується офіційний екшн `actions/checkout@v4`.
2. **Встановлення середовища з кешуванням**: `actions/setup-node@v4` з параметром `cache: npm`. Це пришвидшує встановлення залежностей у кілька разів.
3. **Детерміноване встановлення пакетів**: команда `npm ci` гарантує точну відповідність залежностей файлу `package-lock.json`.
4. **Виконання юніт- та інтеграційних тестів**:
   ```bash
   npm test -- --test-reporter=spec --test-reporter-destination=stdout \
              --test-reporter=junit --test-reporter-destination=junit.xml
   ```
   Усі 13 тестів (авторизація, створення замовлень, ідемпотентність, аудит-лог, відгуки) виконуються успішно.
5. **Збереження артефакту звіту**: файл `junit.xml` завантажується як артефакт збірки через `actions/upload-artifact@v4` і доступний для перегляду та аудиту.
6. **Формування Job Summary**: у вкладці запуску виводиться звіт із версією Node.js та коротким SHA коміту.

---

### 3.4. Етап 2: Збірка та публікація образу (`job: publish`)
* **Умова запуску:** виконується тільки після успішного проходження тестів (`needs: test`) і тільки для гілки `main` або тегів (не для сторонніх PR).
* **Автентифікація в GHCR:**
  Використовується вбудований системний токен GitHub:
  ```yaml
  - name: Log in to GHCR
    uses: docker/login-action@v3
    with:
      registry: ghcr.io
      username: ${{ github.actor }}
      password: ${{ secrets.GITHUB_TOKEN }}
  ```
  Це виключає необхідність створення та збереження сторонніх персональних токенів (PAT) і гарантує високу безпеку.
* **Збірка образу через Buildx**: `docker/build-push-action@v6` виконує збірку та відправляє образ у GHCR із кешуванням шарів через механізм GitHub Actions Cache (`type=gha`).

## 4. Бейдж статусу та опис у README.md

У файлі [`README.md`](../README.md) розміщено бейдж актуального статусу виконання пайплайну:
```markdown
[![CI/CD](https://github.com/<owner>/<repo>/actions/workflows/ci.yml/badge.svg)](https://github.com/<owner>/<repo>/actions/workflows/ci.yml)
```
Якщо всі тести пройшли і образ успішно зібрано, бейдж відображає зелений статус `passing`.

## 5. Відповіді на поширені контрольні запитання

### 1. Чи можна реалізувати delivery без Docker?
**Так.** Для рівня 75 балів методичка допускає Варіант B (збереження зібраного бінарного артефакту або архіву через `actions/upload-artifact`). Проте Варіант A (GHCR) є галузевим стандартом, оскільки контейнерний образ готовий до безпосереднього розгортання в Kubernetes або Docker Compose на будь-якому сервері без додаткового налаштування оточення.

### 2. Як заборонити злиття pull request без успішного (зеленого) CI?
У налаштуваннях репозиторію на GitHub:
1. Перейдіть у **Settings ➔ Branches ➔ Branch protection rules**.
2. Додайте правило для гілки `main`.
3. Увімкніть пункт **«Require status checks to pass before merging»**.
4. У списку обов'язкових перевірок відзначте задачу `Test`.
Після цього кнопку «Merge pull request» буде заблоковано, доки всі тести у workflow не виконаються зі статусом success.

### 3. Чи достатньо стандартного GITHUB_TOKEN для публікації у GHCR?
**Так, цілком достатньо.** 
У межах робочого репозиторію вбудований `secrets.GITHUB_TOKEN` має всі необхідні права за умови явної вказівки блоку `permissions: packages: write` у секції джоби. Створювати персональний токен (Personal Access Token, PAT) не потрібно, що запобігає ризику витоку довготривалих ключів.

### 4. Чому тести локально проходять, а в середовищі CI можуть падати?
Основні причини:
* **Різниця версій:** різна версія Node.js або системних бібліотек (наприклад, локально стоїть Node.js 18 на Windows, а в CI запускається Node.js 22 на Linux).
* **Недетерміноване встановлення залежностей:** використання `npm install` замість `npm ci`, що може підтягнути нові мінорні версії бібліотек з помилками.
* **Чутливість до регістру символів у шляхах:** файлова система Windows нечутлива до регістру (`Index.js` == `index.js`), тоді як у Linux це дві різні назви файлу.
* **Різниця в таймзонах:** локальний комп'ютер використовує часовий пояс GMT+2/3, а CI-раннер працює в UTC.

### 5. Як пришвидшити виконання CI-пайплайну?
1. **Кешування залежностей**: директива `cache: npm` у кроці `setup-node` зберігає глобальний кеш пакетів між запусками.
2. **Кешування шарів Docker**: параметр `cache-from: type=gha` та `cache-to: type=gha` у `build-push-action` дозволяє не перезбирати незмінні шари образу.
3. **Паралелізм та раннє скасування**: використання `concurrency` з `cancel-in-progress: true` для автоматичної зупинки застарілих збірок.
4. **Використання легких базових образів**: заміна повних дистрибутивів на `alpine` або `slim` пришвидшує скачування та збірку образів.
